## R201 — Recurrence storage: one canonical rule string, emitted only by the server

**Decision**: A repeat is stored as **one RFC 5545 rule per series** in `events.rrule` — plain `text`, without the `RRULE:` property prefix, DTSTART never embedded (the event's own `starts_at`/`start_date` is the anchor, matching the reference). The emitted grammar is closed and the field order fixed: `FREQ=…;INTERVAL=1[;UNTIL=…][;WKST=…][;BYDAY=…|;BYMONTHDAY=…]` — `INTERVAL=1` always written, `WKST` on weekly rules only (from the household's start-of-week, `SU` default), `BYDAY`/`BYMONTHDAY` always explicit so a stored rule is self-describing. `UNTIL` is a plain date (`YYYYMMDD`) for all-day series and the **household-zone last instant of the chosen end date converted to UTC** for timed series; inclusivity is enforced in the expander by **local-date comparison** (occurrence's household-zone date ≤ UNTIL's household-zone date), never by instant comparison. **Clients never send a rule string**: the form submits the structured choice (`{repeat, weekdays?, until?}`), Zod-validated at the action boundary, and the server action's emitter is the sole producer. The parser is strict — the grammar above verbatim, `INTERVAL=1` only, no `COUNT`, nothing unknown — with the database's `^FREQ=` / no-`COUNT` CHECK as the backstop.

**Rationale**: FR-231/232 close the grammar completely — four choices, no every-N, no count — so with `INTERVAL` pinned at 1 every rule is a stateless per-local-date predicate (a date matches DAILY always, WEEKLY iff its weekday is in BYDAY, MONTHLY iff its day-of-month equals BYMONTHDAY), and a series can produce **at most one occurrence per local date**, which R204's exception key leans on. FR-233 requires the reference's format survive: the observed reference rules `[verified]`(skylight-api) are exactly this shape and field order (`FREQ=WEEKLY;INTERVAL=1;UNTIL=20260106T235959Z;WKST=SU;BYDAY=MO,TU`), so our strings are byte-plausible Skylight rules. The one deliberate divergence: the reference's observed `T235959Z`-on-the-date UNTIL is subtly wrong for evening events west of UTC (`20261217T235959Z` is 17:59:59 CST — it drops an 18:30 occurrence on the until-date itself); our household-zone end-of-day form is RFC-correct and round-trips, and the expander's date-level inclusivity rule still expands a genuine Skylight `T235959Z` rule correctly, so an imported reference rule both survives *and* renders right. Emitter-only production kills rule injection and parse-mismatch as a class; a stored unparsable rule is a bug, not a user path.

**Alternatives rejected**: `text[]` with the `RRULE:` prefix, mirroring the wire shape — fidelity to an array that never held a second element in any observed row; a scalar is honest and mechanically reversible. A `FREQ` whitelist in the CHECK — the interface offers four choices but storage must accept a richer Skylight rule (FR-233's "the simpler interface discards nothing"). Instant-compared UNTIL — drops the same-evening occurrence the reference's own habit drops; date semantics are what FR-232's words ("a date after which no occurrence appears") say.

## R202 — Expansion: hand-rolled in `lib/family/recurrence/`, no date or recurrence library

**Decision**: Hand-roll the subset in three dependency-free, pure modules: `grammar.ts` (strict parser + canonical emitter, ~80 lines), `zone.ts` (`Intl.DateTimeFormat`-based offset math: `zoneOffsetMs`, `instantToWall`, `wallToInstant` with the gap/fold policy, ~90 lines), `expand.ts` (the stateless date-walk applying exceptions, ~100 lines). Expansion converts the series start to household-zone wall clock once, walks local dates over the padded window keeping rule-matching dates within `[start, UNTIL]`, converts each back to an instant, and applies the duration in instant space. The zone policy is exactly FR-235/236: `wallToInstant` probes candidate offsets — one candidate is normal time; two (a fall-back fold) takes the **first instant**; zero (a spring-forward gap) binary-searches the transition and lands on its **edge** — a 02:30 event on the gap date renders once at **03:00**, the first valid time on that date. Duration applied in instant space gives the fall-back edge case for free (an event running through the repeated hour occupies the true elapsed wall-clock time). One implementation runs identically in the browser (rendering cached rows) and in server actions (validating occurrence keys).

**Rationale**: The four-choice grammar makes the recurrence arithmetic ~30 lines — the actual engineering risk is zone math, and FR-235's "first valid time on that date" is a semantic **no candidate library produces**: `rrule` has no gap model at all, Luxon and Temporal's `compatible`/`later` disambiguation give 03:30, `earlier` gives 01:30. Since the ~25 lines of gap/fold policy are ours under every option, the only question is whether to carry a dependency for a date-walk and a 15-line offset lookup. The module shape is also what the repo's gates want: small pure functions nowhere near the cyclomatic/cognitive budgets, the canonical CRAP case (branchy and pure) written test-first against golden DST tables (R213), and zero bytes added to a PWA that ships no date library today `[verified]`(package.json). `Intl` with full ICU is guaranteed in every target (browsers; Node ≥ 14 for Vitest and server actions); the formatter is cached per zone and a week's expansion is thousands of µs-scale calls at worst.

**Alternatives rejected**: **`rrule`** — `[verified]`(npm registry) latest 2.8.1, published 2023-11-10, no release in nearly three years; 13.1 KB gzip including an English-NLP module we would never call `[verified]`(bundlephobia). The disqualifier is its documented date model — "fake local time encoded as UTC" — which forces exactly our zone math around every input and output, and its DST-with-`tzid` record is a live open-issue trail (#294, #355, #550, #523, #621) whose subject line is precisely SC-208's failure mode ("09:00 on both sides of every DST change… no occurrence missing or duplicated"). **Temporal via `temporal-polyfill`** — 19.8 KB gzip `[verified]` on every tablet load while native support can't yet be assumed; contains no RRULE layer; its disambiguation options bracket but never hit the 03:00 edge. Deliberately kept cheap to adopt later: `zone.ts` is the single ~90-line swap-out file when Temporal is native everywhere. **Luxon / date-fns-tz for zone math only** — Luxon is 21.9 KB gzip and its gap behaviour (shift-through, 03:30) contradicts FR-235; `date-fns-tz` is a genuinely cheap 3.3 KB but replaces ~20 lines while the tested gap/fold surface stays ours — a dependency for its own sake, and the first thing to reach for if the zone layer ever grows real scope.

## R203 — The household timezone (FR-284): one column on `household_settings`, seeded, read-only

**Decision**: `013_household_timezone.sql` adds `family.household_settings.timezone text not null default 'UTC'` plus a validity trigger (`pg_timezone_names` lookup — a CHECK is illegal because the catalog view is not immutable), same SECURITY DEFINER / revoke-from-public shape as every Phase 1 trigger function. The **real** zone is written by `scripts/family-seed.mjs` (from `FAMILY_SEED_TIMEZONE`, defaulting to the machine's resolved zone), never by committed SQL. Nothing else joins the migration: none of the data brief's seven calendar-toggle columns ship, because the final spec fixed all of that behaviour in code (FR-215, Assumption 16). The column is read-only this phase — no action writes it. Every rendering (FR-219) and every occurrence a rule produces (FR-234) is worked in this zone; the per-event `timezone` column stays what FR-224 says it is — creating-device provenance that nothing renders or expands from.

**Rationale**: Phase 1's data-model names `household_settings` as exactly this extension point ("calendar-specific settings arrive with Phase 2 as an `alter table`"), and the spec's own Key Entities files the timezone under *Household calendar preferences*, in the same 1:1 record as the start-of-week preference the same grid read already fetches — one settings read serves FR-203 and FR-284 together. Keeping household-specific configuration out of committed SQL is Phase 1's seed discipline (constitution §VII); and `'UTC'` as the un-seeded fallback fails *loudly* — every event an hour or six off — rather than plausibly, which is what you want from a placeholder.

**Alternatives rejected**: A column on `households` — a defensible reading of "kept with the household", but it splits the calendar's settings across two tables and re-opens a closed Phase 1 shape. Hardcoding the operator's real zone as the default — household configuration in version control. Shipping the toggle columns now "while we're in there" — Phase 1's rule is that unused columns don't ship early; they arrive with the settings interface that reads them.

## R204 — Exceptions and splits: date-keyed rows, self-contained segments, no lineage

**Decision**: `family.event_exceptions` holds one row per diverging occurrence — `action in ('skip','override')` — keyed by a **single `occurrence_date date`**: the occurrence's *original* date in the household's timezone, with `unique (event_id, occurrence_date)`. An override may carry exactly FR-239's four fields — time (either shape: `starts_at/ends_at` or `start_date/end_date`), title, place, notes — as nullable columns where null means inherit; CHECKs force a skip to carry nothing and an override at least one thing, and time pairs to be coherent. No categories on exceptions, structurally (FR-287 — a per-occurrence recolour is unrepresentable, which is the spec's intent made mechanical). A `this_and_future` **edit** on occurrence O: if O is the first occurrence, apply to the series in place (FR-241); otherwise re-emit the original's `UNTIL` as O's local date − 1, insert a **fully self-contained new series row** starting at O with the edit applied (categories copied, original UNTIL carried), and re-home exceptions with `occurrence_date ≥ O` onto the new row — keys unchanged, they are dates. A `this_and_future` **delete** truncates the same way and deletes exceptions dated ≥ O (FR-286); on the first occurrence it deletes the series. **No lineage column** (`split_from_event_id`) ships. The multi-statement split is made atomic by routing it through **one SECURITY DEFINER RPC** (`family.split_event_series`, Phase 1 function discipline — `search_path = ''`, revoke from public, execute for `service_role` only); its migration home is fixed in data-model.md.

**Rationale**: The closed grammar guarantees at most one occurrence per series per local date (R201), so an instant key is over-specified — and actively worse: a series-level time change ("all events: 17:00 → 18:00") silently orphans an instant-keyed override, while the date key keeps it attached, which is the spec's stated intent for the record ("stays attached to the right occurrence when the series changes"); an occurrence sitting on a DST transition moves its *instant* (FR-235) while its date stays put; and FR-286's "dated on or after" becomes one indexed date comparison. The lineage column is dropped because the spec itself answered the question: FR-242 and Assumption 27 define "all occurrences" as **segment-scoped** — after a split a series "is thereafter two series", stated in the interface's wording — so no requirement ever walks a chain, and Phase 1's rule against unused columns governs. The atomicity call is made against Phase 1's own precedent: 001 shipped two knowingly non-atomic multi-statement actions with the shape documented, but a half-completed split (a truncated series missing its tail) is a *wrong calendar*, which Story 1 calls worse than no calendar — so this one goes through Postgres in one transaction.

**Alternatives rejected**: Instant-keyed exceptions (RECURRENCE-ID style, and the data brief's split `occurrence_date`/`occurrence_start` pair) — orphaned by series-level time changes, detached by DST instant drift, redundant under the one-per-date guarantee; returns as a migration only if sub-daily or every-N rules ever ship. A lineage chain — only needed if "all" crossed splits, which FR-242 forbids; one nullable `alter table` restores ancestry if a later phase wants it. Detaching a `this`-scope edit into a standalone event — rejected by the spec (Assumption 26): a later series change must still reach every field the occurrence did not override. The split as multi-statement action code — see above; the RPC costs one function and buys the invariant.

## R205 — Drag: hand-rolled Pointer Events over two pure modules; @dnd-kit stays in colectivo

**Decision**: Build the drag layer on **Pointer Events + `setPointerCapture`** over two pure, framework-free modules: `lib/family/week-geometry.ts` (a `GridMetrics` snapshot type measured by the grid, px↔minutes, `snapToStep` 15-minute rounding, `slotFromPoint` hit-testing across columns / all-day band / invalid targets, `planMove` / `planResize` producing candidates that enforce duration preservation, the one-step minimum, non-inversion and FR-251's conversions, and `autoScrollVelocity`) and `lib/family/drag-state.ts` (a reducer — `idle → armed → dragging → confirming → committing` — with every cancel path an explicit transition and no DOM, cache or network access; it emits intents). The DOM adapter is thin: `useEventDrag.ts` wires pointer events with capture **on the grid's stable scroll container** (so a realtime refetch unmounting the source block mid-drag dispatches `SOURCE_GONE` instead of stranding the gesture), rAF-throttles moves, and runs the auto-scroll loop. Activation is distance-slop (~8 px), never a timed hold (FR-253); blocks carry `touch-action: none`, the grid background keeps `pan-y`, and the slice pager ignores pointer-downs that begin on a block — the gesture systems partition the surface by target, not by timing. The preview is a **snapped in-grid ghost** (the shared `EventBlock`, `aria-hidden`, rendered by the grid from reducer state) with the source block dimmed in place; the only tween (settle on commit/revert, framer-motion) is gated on `useReducedMotion()` (FR-252). The keyboard path feeds the **same reducer** (Alt+Arrow move, Alt+Shift+Arrow resize, Enter commits into `confirming`, Esc cancels) with slot-semantic `aria-live` announcements, over the always-available details→edit baseline. **@dnd-kit is not used for the calendar** — not the installed 6.3.1 line, not the experimental rewrite; it stays exactly where it is (colectivo's sortable list). This supersedes the client-flow draft's "@dnd-kit sensors own block presses" line.

**Rationale**: Resize decides it — FR-245's edge-resize sits wholly outside dnd-kit's translate-a-draggable model in both lines `[verified via context7]`, so with dnd-kit the phase would run two parallel gesture systems for one feature. The geometry is ours in every variant: snap in household-local minutes, duration-preserving grab offsets, midnight-crossing segments (FR-217), band↔grid conversion, and DST placement are calendar math no drag library provides — once `slotFromPoint`/`planMove`/`planResize` exist, dnd-kit's residual contribution is a pointer dispatcher worth ~60 lines of platform code. The installed line is now documented as legacy and its successor is pre-1.0 `[verified via context7]` — neither is a foundation for the phase's flagship gesture. And the gates want this shape: the branchy parts (hit-testing, snapping, the state machine) live in pure modules with exhaustive unit tables, mirroring 001's pure-module-plus-thin-binding pattern. The stated trade is recorded rather than hidden: with `touch-action: none` on blocks, a scroll or slice-swipe cannot *start* on an event block — the household scrolls from the hairline gaps, gutter or header; verified by hand on the iPad.

**Alternatives rejected**: `@dnd-kit/core` 6.3.1 with per-column droppables and custom modifiers — no resize; its transform/DragOverlay model fights the snapped in-grid ghost; its snap modifier snaps pixel transforms, not minutes; collision detection reduces to "which column", which `slotFromPoint` already answers. The `@dnd-kit/abstract`/`@dnd-kit/react` rewrite — 0.1.x, a *new* dependency despite the name, still resize-less. `dnd-timeline` — horizontal-timeline-oriented, small community, same resize-less core. Long-press activation — forbidden outright by FR-253/Contradiction 3. Keyboard drag as simulated pixel movement — slot-semantic `KEY_MOVE` through the one reducer gives calendar-language announcements and one state machine to test, not two input systems to reconcile.

## R206 — The week-window read: three-branch OR over real columns; expansion client-side in one non-bypassable module

**Decision**: The week is **one RLS-governed round trip per anchored week**: `fetchWeekEvents` selects, for the household, every series row unconditionally (`rrule is not null`) plus one-off rows whose real bounds overlap the window (timed by `starts_at`/`ends_at`, all-day by the inclusive date pair) — a three-branch PostgREST `or()` served by three partial indexes — with `event_categories` and `event_exceptions` embedded, explicit column lists per the Phase 1 read contract (no `select('*')`, explicit `.eq('household_id', …)` even under RLS). **No derived `search_start`/`search_end` columns and no window trigger ship** — this supersedes the client-flow draft, which was written against the data brief's maintained-search-window read; its widen-on-write contract is void. Expansion is client-side in **one non-bypassable entry point**, `expandWindow(events, window, householdTz)` in `lib/family/calendar/expand.ts` (framework-free; composed from R202's `expandSeries`), memoized **once per mounted week** in `useWeekOccurrences`; filtering and layout are separate memo layers above it, so toggling a filter never re-expands. `expandWindow` handles the moved occurrence completely: it walks the window's dates applying skips and overrides, **drops an occurrence whose override moved it out of the window, and additionally emits occurrences whose override landings intersect the window even when their original dates fall outside it** — possible precisely because every series row always arrives with *all* its exceptions embedded.

**Rationale**: The classic recurrence-in-a-window problem (an unbounded weekly series whose row's `starts_at` is years in the past) is dissolved honestly at this scale rather than engineered around: a family accumulates series in dozens, not thousands (~600 rows ≈ 120 KB even at ten new series a month for five years, with the realistic count far lower), while one-off history is windowed by real bounds so it never accretes into the payload (~50 rows per week view instead of ~2,600 after five years). Dropping the derived columns dissolves two problems the data brief had to patch: the **moved occurrence** (found because the series row and its exceptions are always fetched — no fetch-window padding number ever needs to exist, and no write path has to remember to widen anything) and the **rrule-parser-in-PL/pgSQL** (the window trigger needed to parse `UNTIL` out of rule text — a second recurrence implementation that can drift from the JS one, exactly the two-implementations trap). The honest ceiling is stated: O(all series + windowed one-offs) per read, right for one household and wrong for a multi-tenant SaaS; if a later phase's server-side reminder scan forces a materialised occurrence table, it arrives additively — the series row stays the source of truth either way. One expansion entry point (guarded by a fallow boundary so components cannot import the recurrence internals directly) means no renderer can disagree with another about what an occurrence is; a full re-expand at this scale is sub-millisecond, so per-series memo caches would be complexity chasing a cost that does not exist.

**Alternatives rejected**: Trigger-maintained `search_start`/`search_end` (the data brief's and client-flow draft's proposal) — the PL/pgSQL rrule parsing, the trigger surface, and a write-path contract every future write must honour, to optimise a read that is ~50 rows without them. A `daterange` + GiST index — an extension and range machinery for the same non-problem. Materialised occurrence rows (what the reference verifiably does server-side) — needs a horizon, a backfill job and a second write path that can drift; the spec's Key Entities already forbids stored occurrences. A padded fetch window plus a second exceptions query — two round trips and client-side join logic, strictly worse than embedding.

## R207 — Cache identity: the anchored week, prefetched neighbours, server-seeded first paint

**Decision**: The cache unit is the **anchored week, never the phone slice**: `familyKeys.week(householdId, weekStart)` = `["family", "events", householdId, "2026-09-13"]`, where `weekStart` is the household-start-of-week date as a plain `YYYY-MM-DD` in the household's timezone — one canonical key per week however it was reached (swipe, arrows, Today, midnight rollover). Both new keys live under the `["family"]` prefix, so Phase 1's bare invalidation — the realtime handler *and* `withActor`'s success-path `refresh()` — sweeps them with **zero changes to either mechanism**. `useWeekEvents` mirrors Phase 1's hook shape (`staleTime` 30 s, default `gcTime` letting abandoned weeks fall out of memory on the wall tablet). When the anchor settles on a week, adjacent weeks (`weekStart ± 7 days`) are prefetched; swiping within a week costs zero fetches because the whole week is already cached. The calendar's `page.tsx` (server component) fetches the current week with the server client and passes it as `initialData` — the same no-flicker first paint as the Phase 1 shell.

**Rationale**: FR-289 makes "the displayed week" the real object and the slice a viewport onto it; per-slice keys would duplicate day data across overlapping entries (slices overlap by construction — R211) and turn the swipe path into a cache-assembly problem. Slotting under `familyKeys.all` is the whole point of Phase 1's prefix-swept key design: the invalidation machinery works on day one with no new code. Prefetch is what makes the week-boundary swipe land on warm data (FR-279); the anchored-week model is what makes same-week swipes free.

**Alternatives rejected**: Per-slice or per-day keys — see above. A month-window key (five weeks per fetch) — fewer fetches, but it breaks the clean week-anchor identity and refetches five weeks on every invalidation; prefetch already hides the boundary. Narrowing realtime invalidation to `familyKeys.events` — a one-line change if it ever matters; starting narrow would fork the invalidation path for no measured benefit.

## R208 — Writes: pessimistic everywhere, a pending overlay for drag only

**Decision**: **No optimistic cache writes anywhere in the calendar** — no `setQueryData` fabrication, no `onMutate` rollback dance. Every write (form save, delete, drag commit) is `withActor(() => eventAction(payload))`: Phase 1's interceptor supplies punch-in-on-demand (FR-270), the lapsed-cookie retry (FR-275), and cache invalidation on success. Forms and deletes show a busy state until the action resolves; failures land against the field (FR-262) or as the FR-288 messages (offline; event already deleted → the form closes). Drag is the one place a bare refetch would look wrong (the block would snap back between action success and refetch arrival), so the drag layer keeps the dropped block rendered at its target — visually *in flight*, never *saved* — from drop until the post-invalidation refetch resolves, then releases it to the fetched truth; on failure or a dismissed prompt it releases immediately and the block is where the cache always said it was (FR-249: nothing was ever written, so there is nothing to roll back). Prompt order on a repeat's occurrence is fixed by FR-250: scope dialog first (one `ScopeDialog` component shared verbatim by edit, delete and drag), punch-in second, and dismissing either abandons the pipeline with nothing written.

**Rationale**: FR-288's wording is blunt — nothing may be *shown as saved* that is not saved — and the scope writes make cache surgery genuinely dangerous anyway: a `this_and_future` edit splits a series into two rows and re-homes exceptions (R204), which no hand-patched cached week can mirror safely; a forgotten code path there is exactly the wrong-calendar bug Story 1 ranks worse than no calendar. SC-206's one-second budget is met without optimism: the pending overlay plus a sub-second action plus one small refetch. The design also makes rollback trivial by construction — discarding derived state — so a half-failed drag cannot corrupt the cache.

**Alternatives rejected**: True optimistic updates with rollback — rejected on FR-288's letter and the multi-row surgery risk; the perceived speed they buy is already delivered by the overlay. Queueing offline writes — forbidden by FR-288 and Assumption 38 (the offline cache is a later phase; pretending otherwise is a lie the household could act on).

## R209 — Realtime: three tables join the existing channel, unfiltered, as bare invalidation

**Decision**: `014_realtime_calendar.sql` adds `events`, `event_categories` and `event_exceptions` to the `supabase_realtime` publication inside the Phase 1 guard (NOTICE-and-return when the publication is absent; per-table existence checks; closing `notify pgrst, 'reload schema'`). **Replica identity stays at the default (primary key)** — `replica identity full` is prohibited, because Realtime does not apply RLS to DELETE payloads and a deleted event's `summary` is precisely the child's-schedule data constitution §VII protects. Client-side, the three tables extend the `TABLES` list in the existing `useFamilyRealtime` channel **without the `household_id` server-side filter** (the `filter` member becomes optional), and every notice funnels into the existing `invalidateQueries(familyKeys.all)`. No payload is ever rendered.

**Rationale**: Assumption 39 already resolved this: with default replica identity a DELETE payload carries only primary-key columns — never `household_id` — so Phase 1's filtered subscription would silently never fire on deletes of these tables, and SC-204 (a moved occurrence on device B within 5 s) plus the "later write wins" edge case both ride on deletes and updates arriving. Unfiltered is safe here because the payload is treated purely as "something changed, re-read": INSERT/UPDATE payload *content* is never used, the re-read goes through the RLS-governed window query, and the household is this project's only tenant. This is provider code plus one migration — no dashboard step, matching R210's finding in the schema research that the whole phase needs nothing beyond `supabase db push` and the seed.

**Alternatives rejected**: Promoting replica identity to a `household_id`-bearing unique index to keep the filter — more schema to serve a filter a single-tenant project doesn't need. Mapping notices to specific week keys — requires client-side bookkeeping about which weeks contain which event ids, against a payload that cannot be trusted for content; bare invalidation at one household's write rate is a handful of small queries a day.

## R210 — The displayed week: a `{today | pinned}` anchor derived from the existing clock

**Decision**: The displayed week is a two-state anchor — `{ kind: "today" } | { kind: "pinned"; weekStart }` — held by `useWeekAnchor`. While `kind` is `"today"`, the shown week is **derived** from `useNow()` (Phase 1's minute-resolution clock store, reused, not duplicated) converted to the household's timezone; any navigation that crosses a week boundary (swipe, arrows) pins an absolute `weekStart`; a same-week slice swipe updates only the slice index and does not pin; **Today** (FR-281) sets `kind: "today"` and the slice containing today (FR-289). `NowLine` subscribes to the same store alone and repositions each minute (FR-208); `DayColumn` derives past-dimming at minute granularity (FR-215). The slice index is clamped when the column count or the anchor week changes. No new timers exist anywhere in the calendar.

**Rationale**: FR-210 has a sharp qualifier — the week advances at midnight *only while the current week is on show*, so a person three weeks ahead is not yanked back — and the anchor makes that a type-level property instead of a timing bug: nothing a pinned view renders derives from `now`, so midnight cannot touch it, while the `today` state rolls the grid, the dot and the line over by derivation, with no effect code at all. `useNow` already solved midnight once (the Phase 1 top-bar date) and re-reads the clock on first subscribe after idle; the calendar adds only a timezone conversion (FR-284/219 — on the wall tablet device and household agree; on a travelling phone the household clock is the correct one for the today column, the now-line and dimming).

**Alternatives rejected**: A dedicated `setInterval` in the calendar — two clocks drift, and the existing store publishes at minute resolution and cleans up after itself. Effect-driven rollover (watch the clock, imperatively advance state) — exactly the fragile shape the derivation avoids; the "don't yank the navigated user" rule would be an `if` someone forgets instead of a structural impossibility.

## R211 — Phone slice mechanics: pointer-controlled paging, not CSS scroll-snap

**Decision**: The grid renders the anchored week's columns for the current slice; a horizontal pan (framer-motion drag on the grid container — already a dependency, honours `useReducedMotion`) translates the strip and, on release past a threshold, advances **exactly one slice**: left = later, right = earlier (FR-279), from a week's last slice into the next week's first. Slice tiling is pure lib (`sliceStarts(columns)` — at three columns `[0, 3, 4]`: tiled from the week's first day with the last slice pulled back to end on the week's last day, FR-289), and "the slice containing today" resolves to the first match when the overlap makes it ambiguous. Axis lock: the pan claims the gesture only when horizontal displacement dominates (≈10 px and |dx| > |dy|); otherwise the native vertical hour scroll wins (FR-280). The pager ignores pointer-downs beginning on an event block — R205's drag layer owns those; the surfaces partition by target. Column count comes from measurement (`ResizeObserver`): ≥ 1024 pt landscape → 7 (FR-277); otherwise as many whole columns as fit, floored at 3 (FR-278). Reduced motion turns the slice transition into an instant jump (FR-252). Cross-week reach during a drag is edge-hold paging (~40 px zone, ~600 ms) — legal under FR-253, which forbids a timed hold only for *starting* a drag.

**Rationale**: FR-289 kills scroll-snap by itself: the pulled-back last slice makes snap positions **overlap** (day offsets `[0, 3, 4]` — Thursday and Friday appear in two slices), which a linear snap ribbon cannot express; a fling can jump multiple slices against FR-279's one-per-swipe rule; and three gesture systems (vertical hour scroll, horizontal paging, block drag) sharing native scroll physics is a conflict surface with no state machine to arbitrate it. Controlled paging makes the slice a state value — clampable on rotation, derivable for Today, testable as pure tiling maths.

**Alternatives rejected**: CSS scroll-snap — above. A free-running N-day window — forbidden by FR-289 (the anchored week is what keeps "the displayed week" meaningful on a phone). Paging by whole weeks on the phone — contradicts decision #7's "three-day slice, swipe to move through the week".

## R212 — Filter extension: Labels ride the existing store; one new FilterSheet section

**Decision**: **The storage layer does not change at all.** Phase 1's `useDeviceVisibility` already stores generic *category* ids (not "profile ids") in `localStorage` under `family:hidden-categories:v1`, already prunes against all category ids — labels included — and already carries the per-device persistence and in-memory fallback FR-266 needs. Label ids simply start appearing in the hidden set; no key version bump, so existing device preferences survive. `FilterSheet` gains a Labels section — same checkbox-row pattern with a colour swatch in place of the avatar, same `setHidden`/`showAll` (the existing Show all already clears both kinds). The visibility rule is lib, not component logic: `isEventVisible(categoryIds, hiddenIds)` in `lib/family/calendar/visibility.ts` — visible when the event has no categories, or when at least one carried category is not hidden (FR-265) — applied to the expanded occurrence list as its own memo layer (R206), display-only by construction (FR-267).

**Rationale**: The Phase 1 store was built label-ready; only its dialog was profiles-only. Extending the dialog in place is the honest reading of FR-264 ("Labels join the existing filter sheet") — and like the FR-274 delete-count amendment, it is an in-place extension of a shipped Phase 1 surface, listed as work rather than claimed as inheritance.

**Alternatives rejected**: A new versioned localStorage key or a parallel `visibleLabels` plumbing — would orphan existing device preferences and duplicate a store that already generalises; the calendar consumes `hiddenIds` directly.

**Rationale**: Constitution §II draws exactly this line — pure logic test-first, drag/visual layers verified by running the app — and the phase was decomposed (R202, R205, R206) so the branchy, silently-data-corrupting parts *are* pure: the recurrence and zone math, the geometry planners, the reducer, the tiling. **Alternatives rejected**: Simulating pointer-capture physics in jsdom — would test the simulation; the metrics-as-input design exists precisely so jsdom tests stop at the seam. pgTAP for the new policies — re-rejected for the reason 001 R10 gives (a second runner for a still-small suite).

## R214 — Dependencies: none added

**Decision**: This phase adds **zero new dependencies**. Recurrence, zone math and expansion are hand-rolled (R201/R202); drag is hand-rolled on platform Pointer Events (R205); the slice pager and settle animations use `framer-motion` (already installed, `[verified]` package.json ^12.23); `@dnd-kit/*` remains installed for colectivo and is not imported by any calendar file; everything else (TanStack Query 5, Zod 4, jose, `@supabase/ssr`) is the shipped Phase 1 stack.

**Rationale**: Each candidate was weighed in its own entry with sizes and maintenance status verified this session (R202: `rrule` 13.1 KB gzip/unmaintained, `temporal-polyfill` 19.8 KB, `luxon` 21.9 KB, `date-fns-tz` 3.3 KB; R205: the installed dnd-kit line documented as legacy, the rewrite pre-1.0). In every case the irreducible hard part — the gap/fold policy, the grid geometry — stayed ours, so the dependency would have carried bytes without carrying risk. The one planned re-entry point is explicit: `zone.ts` is shaped to be swapped for native Temporal when it can be assumed everywhere.
