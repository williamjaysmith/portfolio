# Implementation Plan: Family Tasks

**Branch**: `003-family-tasks` | **Date**: 2026-09-04 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/003-family-tasks/spec.md`

## Summary

Build the Tasks tab for `/family` on the shipped Phase 1 + Phase 2 platform: one self-measuring column per Profile showing one day (wrapping on a portrait tablet, paging on a phone, Up for Grabs left-most), four sections per column with clock-driven time-of-day toggles, chores in their four derived sub-types and routines in their slots, both of the reference's repeat modes, late carry-forward, skip and unskip, up-for-grabs claiming, habit streaks, five filters plus search, and the seventeen-template Task Box — with a punched-in actor required for every write and recorded beside the Profile credited.

The technical core is **three decisions that keep one implementation where the spec would tolerate two**. The shipped recurrence grammar is **widened in place** to `INTERVAL=1–99` rather than forked — one parser, one emitter, one anchor-relative predicate serving events, Scheduled Date chores and routines, with a `ruleDatesIn` primitive extracted so `expandSeries` and the tasks walk share the same rule engine (R301–R304). **Completed Date stores nothing about the future**: it is a linked chain of resolutions whose open occurrence is derived by a pure function from the chain tail, published as the schema's first view — which turns FR-344's undo refusal into a foreign key and FR-370's single claim into a unique index, and makes every mid-cycle edit move the pending occurrence for free (R308–R310). And **the board's counters branch above every display filter** in one memo chain over one non-bypassable expander, so "filters never move the counters" — said four times in the spec — is a property of the graph rather than an `if` in four components (R315–R318).

This phase adds **seven migrations (017–023), zero dependencies, and no new write plumbing**: every verb rides Phase 1's `withActor` → server action → bare-invalidation machinery unchanged, there is no new timer anywhere, and **no database function is on the write path** — complete and skip are one INSERT, undo is one DELETE, because the derived cursor left nothing for an RPC to hold (`data-model.md`, `contracts/server-actions.md`; R310 superseded). It amends four shipped surfaces in place and changes the contract of **two** shipped Phase 1 modules: `permissions.ts` gains its first decision that depends on *which record* is touched, and `guards.ts` gains `requireVerifiedActor()` — the row-reading half of `requireParent` extracted, so FR-351 is decided from the database role and not the cookie's.

### Re-check after Phase 1 design

Design introduced five things worth re-testing against the constitution:

- **The schema gains its first view, and it is the read path for a mode's correctness.** Tested against §VII: `family.task_cursors` is `with (security_invoker = true)`, so the caller's own RLS on `family.task_resolutions` and `family.tasks` applies and the view grants no reach a member did not already have — it exists only because the row that decides what is due today may lie outside every window the board fetches, and PostgREST cannot express a per-group `limit 1`. It is `select` to `authenticated` and `service_role`, nothing to `anon`, asserted as one new row in the privilege-matrix delta. Re-check: **PASS**.
- **A resolution now changes what appears on *future* days.** Phase 2's expansion is pure in the stored rows, so a write only ever invalidated the weeks it touched; completing a Completed Date occurrence *creates* tomorrow's. Tested against §VI: Phase 1's bare `invalidateQueries(familyKeys.all)` already sweeps every task key, so this costs nothing today — but the blunt invalidation is now **load-bearing** rather than merely convenient, and narrowing it later would break this mode first. Recorded in R309 and in the Risks table so a future optimisation trips over the note. Re-check: **PASS**.
- **A shipped Phase 1 module's contract changes.** `permissions.ts` is a pure binary `can(actor, op, ctx)` whose only non-role input is `householdHasParent`; FR-351 is the first rule in this app whose answer depends on *which record* is touched. Tested against §VII and §II: the target enters `PermissionContext`, the module stays pure and framework-free, its unit test grows the four-check matrix SC-304 names, and it remains **affordance only** — the gate is the server action, and FR-350 forbids hiding controls as the mechanism. Assumption 3 names this as work rather than inheritance and the phasing treats it that way. Re-check: **PASS**.
- **Two Phase 0 lanes reached the same question from different ends and disagreed, and the deltas are recorded rather than papered over.** The schema lane proposed a stored `tasks.next_due_date`; the completed-date lane found it demonstrably wrong under FR-324 (one column, two independent cycles) and answered its one real objection with a view. R309 decides, R310 records what shrank as a consequence, and the research preamble names every superseded proposal — including four from the distilled `data.md` brief — where it lands. One document decides each question; the losers say who won. Re-check: **PASS**.
- **The two resolution RPCs did not survive design, and the phase ships no function on the write path.** R310 shrank them to their minimum once the unique index and the `cycle_prev` FK took over the claim race and the undo refusal; design then found the minimum was *nothing*. Complete and skip are one INSERT, undo is one DELETE, and the only companion write left is the streak checkpoint — a second statement whose half-state is a **stale number, not a wrong board**, and which FR-374 already requires be recomputed on the next resolution or undo of that routine, i.e. it self-heals on the very path the requirement names. That is Phase 1's documented non-atomic-action posture, not Phase 2's data-loss bar, so §V/§VII are satisfied without a `SECURITY DEFINER` function, its grants, or a privilege-matrix row. `data-model.md` decides this ("Why there is no `next_due_date`, and no resolve RPC"; "What the database enforces, and what the action does"), `contracts/server-actions.md` states it as a contract ("**No function is on the write path**"), R310 carries a supersession banner naming them, and the residual is in the Risks table below. a task-functions migration does not exist; migration 021 is the Task Box. The Profile-deletion orphan window (R307) is likewise **not** given a function: its half-state retains an unreachable task rather than destroying one and is repairable by re-running the cleanup. Re-check: **PASS**.

### Complexity Tracking

**No deviation is claimed, and none is self-approved.** Constitution §Governance makes Complexity Tracking the place a deviation is *recorded* — and states in the same paragraph that "principles marked NON-NEGOTIABLE cannot be waived by a spec". §I is NON-NEGOTIABLE, so this section cannot be used to authorise an exception to it; what it carries instead is the one question this design puts to the operator, and the reasoning either way.

**Open question for the operator — does §I's "third consumer" rule bind *inside* a sub-app?**

| The move | Why this plan assesses it as a §I pass | What would change if the operator reads §I literally |

**Structure Decision**: The Tasks board replaces its Phase 1 placeholder page inside the existing `(app)` route group, so it sits behind the server gate and inside the provider chain with no new plumbing. The layering rule does the heavy lifting again, and the fallow zone makes it enforceable: everything that can produce a wrong board — the widened predicate, the cursor derivation, expansion and carry-forward, the resolution index, the counters, the visibility rule, the layout decision, the streak rule — is framework-free `lib/family/**` with the components as thin renderers, and `lib/family/tasks/**` is the only new zone permitted to reach the recurrence internals, so R202's confinement survives. Four Phase 1/2 surfaces are amended in place (marked `(~)`) rather than forked, per the spec's own instruction to treat them as work and not inheritance; two further shipped modules change contract — `permissions.ts` (a target-aware decision) and `guards.ts` (`requireVerifiedActor()`, extracted from `requireParent()`).

## Risks

| Risk | Mitigation |
|---|---|
| The widening silently moves a live event | Three checks with three different reaches, stated separately so none is credited with another's coverage. **Algebraic**: `interval: 1` formats in an unmoved slot 2 and `x % 1 === 0`, so the collapse is an identity, not a sample (R302). **Local**: the interval-1 equivalence sweep is ~44 000 evaluations over the whole reachable domain, and the stored-corpus round-trip runs in the **policies** project, which `vitest.config.ts` binds to the local 553xx stack `[code]` — it reads the seeded fixture rules after `db reset`, not one hosted row. **Hosted**: the family's live rules are covered by the operator's read-only query before 022 is written (quickstart §4.2, data-model §023), which must return zero rows; discovery by a failing `ADD CONSTRAINT` on the live database is explicitly not the plan |
| The Completed Date chain tail is the one read that can be silently wrong | A look-back window was rejected precisely because an old tail falls outside it and the chore then reappears **as though it had never been done** — a wrong board produced by an optimisation, with no error to notice. The tail is an exact anti-join in `family.task_cursors`; its ceiling is stated (tens of rows per chore per year) and a materialised tail arrives additively if it ever costs anything (R309) |
| FR-357's 28-day bound composed with FR-343 makes a neglected Completed Date chore unreachable | The mode's open occurrence is exempted from the bound, on Assumption 7's own reasoning; recorded in R316, in the Constitution Check §VIII row, and as a named check in the quickstart, rather than decided inside a component |
| The streak checkpoint is a second statement, so a crash or a race can leave a stale badge | **Accepted residual, and the reason this phase ships no write-path function.** The resolution is one INSERT (or one DELETE); the checkpoint follows it. What can go wrong is a stale *number*, not a wrong board, and FR-374 already requires a recompute on the next resolution or undo of that routine — so it self-heals on the path the requirement names. That is Phase 1's documented non-atomic-action posture, not Phase 2's data-loss bar. The alternatives — an RPC per verb (R310, superseded), recomputing inside a SQL function, or deriving the badge at read time — are a function nobody needs, rule-logic-in-SQL, and an unbounded backward walk respectively |
| A crash between the two statements of a Profile deletion leaves a task with no assignee on nobody's board | Retained data, not lost data, and repairable by re-running the cleanup, so it does not clear Phase 2's wrong-board bar for a function (R307). The fix is pre-specified: one `SECURITY DEFINER` function of its own, doing the category delete and the orphan cleanup in one transaction — at which point a deferred constraint trigger for FR-322 becomes possible too. It would be this phase's **only** write-path function, which is why it is not written speculatively |
| The bare `["family"]` invalidation is now load-bearing, not just convenient | A Completed Date resolution creates a *future* day's occurrence, so narrowing invalidation to a task-specific prefix would break this mode first — and it must sweep all **five** task keys, the cursor read included. Written into R309 and into the realtime module's comment so a future optimisation trips over the note |
| `unique nulls not distinct` requires PG 15+ on the hosted project | Confirmed at the **first operator step, before 022 is written and before any hosted push** — quickstart §4.1, tasks T081(a) — the one moment this is stated, identically, in all three documents; local `config.toml` pins 17, so 018 is proved executable locally at T012 long before the hosted project is touched. The fallback is one `coalesce` expression index with the same guarantee and uglier plans, and it is a **data-model** change: the residual, stated rather than discovered, is that a `false` at T081 costs re-editing 018, a local `supabase db reset` and a re-run of T009–T012 — nothing hosted has been altered by then, which is what makes the late moment survivable |
| **A Vercel deploy that lands before the hosted `db push` takes the shipped calendar's live updates down with it** | The four new tables join the **single shared** `family:${householdId}` realtime channel (T028), and that channel is mounted by `FamilyProvider` on **every** `/family` page; `channel.subscribe()` has no status callback `[code: useFamilyRealtime.ts:50]` and a `postgres_changes` binding for a table the server does not have fails the **whole** channel — so Phases 1 and 2 stop updating live, silently, and `/family/tasks` reads four tables that do not exist with no `error.tsx` anywhere under `app/` to catch it. Mitigated three ways, ordering first: **(1)** the hosted push (T084 / quickstart §4.3) is an explicit, numbered precondition of the merge and the deploy — Hard ordering 7 in `tasks.md`, restated in quickstart §4 and on T084 itself; **(2)** T028 gives `subscribe()` a status callback that surfaces a failed binding instead of leaving the app believing it is live; **(3)** T046's `page.tsx` renders an honest unavailable state rather than throwing when the task reads fail (constitution §VI) |
| Unfiltered realtime means any family-schema write refetches the board | R209's position unchanged and now load-bearing twice: with default replica identity a DELETE payload carries no `household_id`, and this phase deletes on every un-complete and unskip. Bare invalidation at one household's write rate is a handful of small queries a day |
| New branchy lib trips the CRAP gate before its tests land | The phasing order puts tests first for exactly those modules (steps 1, 3, 5); `test:coverage` runs before fallow, as the pre-commit hook enforces |
| `BYMONTHDAY=31` at `INTERVAL=3` produces a six-month gap | Existing behaviour made louder, not a regression (a date that does not exist never matches). Clamping was rejected because it would change shipped Phase 2 behaviour; the gap goes in the form copy so nobody reports it as a bug (R303) |
| The two rule-choice mappers look duplicated enough to trip `fallow:dupes` | They take different unions and apply different constraints, and the shared piece is already `emitRule` (R301). If flagged, the answer is to verify the shared piece really is `emitRule` — never to force a common signature carrying five optional parameters, and never to lift the threshold |
| A future write path stores a rule the expander refuses | Clients cannot send rule strings at all (R201, kept for tasks); the action emitter is the sole producer, 023's bounded regex is the backstop on both tables, and a stored unparsable rule throws as an invariant breach rather than rendering wrongly |
